# Implementation Plan: Drag Section Headings

**Branch**: `045-drag-section-headings` | **Date**: April 23, 2026 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/045-drag-section-headings/spec.md`

## Summary

Allow users to drag act and chapter section headings to new row positions in the plot grid. When dragging, full-width animated drop zones appear at every valid row position. Dropping a section shifts the rows between the old and new position to eliminate gaps, keeping all scenes and other sections in their correct relative order. No new backend endpoints are needed: the existing `PATCH /:storyId/sections/:sectionId` endpoint already handles `verticalIndex` updates with bounded-range grid shifting and `shiftedResources` responses.


Implemented the same way as `draggingScene` in `sceneEditorStore.ts`.

---

### 2. `SectionDropZone.tsx` — new component

Mirrors `SceneActionsCard` but spans all content columns.

**Props**:

```ts
type SectionDropZoneProps = {
  verticalIndex: number;
  draggingSection: Section | null;
  hasSectionAtRow: boolean; // true if another section occupies this verticalIndex
};
```

**Behaviour**:

- `isDisabled` = `!draggingSection` OR `draggingSection.verticalIndex === verticalIndex` OR `hasSectionAtRow`
- Uses `useDroppable({ id: \`section-dz-${verticalIndex}\`, accept: "section", type: "section-droppable", disabled: isDisabled, data: { verticalIndex }, collisionPriority: CollisionPriority.High })`
- CSS: `style={{ gridColumn: "2 / -1" }}` — spans all content columns
- Height classes: `h-0` when `isDisabled`; `h-[20px]` when enabled/idle; `h-[60px] bg-purple-900 text-white` when `isDropTarget`
- Applies `transition-[height] transition-colors duration-250` for smooth animation

---

### 3. `PlotGrid.tsx` — three-pass rendering + drag handlers

#### Pass 0 (new): section drop zones

Inside `grid.map((row, r) => ...)`, before the existing two passes, render a new "Pass 0" for each row. Pass 0 always emits exactly **two** grid cells:

1. `<div className="nbsp" key={...} />` — col-header column placeholder (column 1)
2. `<SectionDropZone key={...} verticalIndex={row[0].verticalIndex} draggingSection={draggingSection} hasSectionAtRow={sectionsHorizontalIndexMap.has(row[0].verticalIndex)} />`

Since every pass emits `gridCols + 1` cells (one col-header + gridCols content cells), the new pass 0 would only emit 2. To keep grid layout consistent, the SectionDropZone uses `style={{ gridColumn: "2 / -1" }}` which spans columns 2 through N, so the row is correctly filled with:

- col 1: nbsp div
- cols 2–N: SectionDropZone (spanning)

This creates one extra CSS Grid row per data row. When `h-0`, the row has no visual height (invisible). This matches the `SceneActionsCard` h-0 pattern from pass 1.

**Top row exception**: The `verticalIndex: -1` corner row does not need a SectionDropZone. Skip pass 0 for `row[0].verticalIndex === -1`.

#### `onDragStart` update

Current: calls `assertIsDraggableSceneData` and fails for section drags; calls `startDraggingScene`.

Updated:

```
if source.type === "section":
  startDraggingSection(source.data.section)
  return
if source.type === "scene":
  if !assertIsDraggableSceneData(data): warn and return
  startDraggingScene(data.scene)
```

#### `onDragEnd` update

Existing scene handler is unchanged. Add a new branch before (or after) the scene handler:

```
stopDraggingSection()   // always called on drag end

if source.type === "section" AND target.type === "section-droppable":
  const { verticalIndex } = target.data
  const { section } = source.data
  if section.verticalIndex === verticalIndex: return  // no-op
  moveSection({ sectionId: section.id, verticalIndex })
```

`moveSection` calls `useUpdateSectionMutation(storyId).mutate({ sectionId, verticalIndex })`.

#### Consuming the mutation

Add `const { mutate: moveSection } = useUpdateSectionMutation(storyId)` inside `PlotGrid` (or in `PlotGridBody` which has access to `storyId`). Since `useUpdateSectionMutation` already handles optimistic updates, `shiftedResources` reconciliation, and error rollback, no additional cache logic is needed.

---

### Shift semantics review

When `useUpdateSectionMutation` is called with a new `verticalIndex`:

1. **Optimistic** (client): `getMoveRangeShift` determines the bounded range; `applyOptimisticShiftToState` shifts scenes and sections in the cache; section's `verticalIndex` updated immediately.
2. **Server** (`updateSectionForStory`): same `getMoveRangeShift` → `shiftGridInVerticalIndexRange` → updates section.
3. **Reconcile**: `applyShiftedResources` applies server-returned shifts; any discrepancy is corrected.
4. **Rollback on error**: `onError` restores both scenes and sections caches from `context.previous`.

#### Example: move act from row 3 → row 6 (moving down)

- Client shift: `{ rangeStart: 4, rangeEnd: 6, shift: -1 }` → rows 4–6 each move up one
- Section moves to `verticalIndex: 6`
- Scenes at rows 4, 5, 6 → now at 3, 4, 5 (gap at 3 is closed; slot at 6 is opened)

#### Example: move act from row 6 → row 3 (moving up)

- Client shift: `{ rangeStart: 3, rangeEnd: 5, shift: +1 }` → rows 3–5 each move down one
- Section moves to `verticalIndex: 3`
- Scenes at rows 3, 4, 5 → now at 4, 5, 6 (slot at 3 opened; gap at 6 closed)
